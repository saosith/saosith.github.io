# saosith.github.io

My professional site and portfolio of analog/mixed-signal IC design work. Built
with [Astro](https://astro.build), deployed to GitHub Pages by GitHub Actions.

Each project is published as a datasheet rather than a gallery: a parameter table
with targets beside results, the test conditions those results were taken under,
a visible badge saying whether the numbers came from a hand model, a simulator or
silicon, and a download link to the dataset behind every plot.

## Before you publish: replace the example content

The site ships with worked examples so every component is visible and working.
**Most of it describes designs that are not yet real.** Work through this list.
Every item is a form in the CMS — the sidebar entry is named in bold.

- [ ] **Resume** — upload your CV. The nav button, the footer and the home-page
      button all read the one path in `src/data/resume.json`, so a single upload
      updates every link.
- [ ] **Site details → Photo** — the hero image. It currently points at a
      **watermarked Unsplash stock file**; replace or clear it.
- [ ] **01 · About → Profile photo** — the square slot beside the About text.
      Empty shows a dashed placeholder.
- [ ] **Now — what you're working on** — one present-tense sentence and a date.
      Ships with placeholder text. Untick *Show* to hide the block entirely.
- [ ] **02 · Experience** — real roles only. Entries ticked *Still a placeholder*
      render a visible "replace this entry" chip. **Do not ship invented
      credentials.**
- [ ] **04 · Awards** — one placeholder entry. Fill it in, or delete it and the
      section renders empty.
- [ ] **07 · Courses** — one placeholder entry, same deal.
- [ ] **03 · Projects** — all three worked examples ship as `draft: true`, so
      **nothing is published yet**, and their numbers are invented. Open one,
      replace the numbers and the write-up, then untick Draft. Until something
      is published the home page shows a placeholder where the flagship chart
      goes, and the projects index says so.
- [ ] `public/data/*.json` — currently generated by `npm run data`, which builds
      **analytical model data, not simulation output**. Replace with real ngspice

- [ ] `public/og.png` — not present. Add a 1200×630 PNG and the social-card meta

## Editing without touching code

The repo is configured for [Pages CMS](https://pagescms.org) — a free, hosted
admin UI that reads `.pages.yml` and commits to this repository on your behalf.
You never see git; saving fires the deploy workflow and the public site updates
a minute or two later.

**Connect it once:**

1. Go to <https://app.pagescms.org> and sign in with GitHub.
2. Grant access to this repository.
3. It picks up `.pages.yml` automatically. No config in the app.

Only people with write access to the repo can log in, so the editor is
effectively private without any extra auth.

**What you get as forms**

The home page is one long scroll, and each of its sections is a separate entry
in the sidebar, listed in the order the sections appear on the page. Editing
Experience therefore cannot rewrite Education, and no form is longer than the
section it edits.

| Sidebar entry | File | What you can edit |
|---|---|---|
| Now — what you're working on | `src/data/now.json` | The dated line under the hero contacts: show/hide, the sentence, the date, an optional link |
| 01 · About | `src/data/about.json` | The paragraphs, plus the square profile photo beside them and its description |
| 02 · Experience | `src/data/experience.json` | Roles: date, title, organisation, logo, body, an evidence link, placeholder flag |
| 03 · Projects | `src/content/projects/*.mdx` | Every frontmatter field as a proper form — spec table rows, headline numbers, tags, footnotes, links, the provenance badge, draft/featured toggles |
| 04 · Awards | `src/data/awards.json` | Same shape as Experience |
| 05 · Skills | `src/data/skills.json` | One row per skill. Rows sharing a group name become one column, in the order the groups first appear |
| 06 · Education | `src/data/education.json` | Same shape as Experience |
| 07 · Courses | `src/data/courses.json` | Code, title, term, note |
| Notes | `src/content/notes/*.md` | Title, summary, date, tags, body (the collection exists, but nothing links to it — both examples are drafts) |
| Resume | `src/data/resume.json` | The CV file and the nav button's label |
| Footer | `src/data/footer.json` | The paragraph under "Use" in the footer |
| Site details | `src/data/site.json` | Name, role, tagline, hero photo and caption, email, phone, profile links |
| Media | `public/uploads/` | Images **and PDFs**, referenced as `/uploads/<name>` |

Two things about `.pages.yml` that are easy to get wrong, both fixed here and
both worth remembering if you edit it:

- **`select` choices go under `options.values`**, as `{ value:, label: }` pairs.
  A bare list directly under `options` silently renders "No options found" with
  no error anywhere.
- **The media block needs `categories: [image, document]`.** Without it the
  picker rejects anything that is not an image, which blocks uploading a PDF
  resume.

**What it deliberately does not do well.** Project bodies are MDX containing
component calls like `<BodeFigure … />`, and notes contain fenced SPICE and
shell blocks. Both body fields are configured as plain text rather than
rich-text, because a WYSIWYG editor would re-serialise that markup and could
mangle it. Editing prose through the CMS is fine; leave the `import` lines and
`<Figure />` tags alone, and write new project bodies in an editor.

New entries take their filename from the title, so a new project called
"Folded-cascode OTA" becomes `folded-cascode-ota.mdx` at
`/projects/folded-cascode-ota/`. New projects default to `draft: true` and stay
out of the build until you untick it.

`_TEMPLATE.mdx` appears in the projects list in the CMS. It is `draft: true`, so
it never publishes — ignore it, or copy it as a starting point.

## Adding anything the site owner has to fill in

**If a change introduces content a person types, uploads, or swaps out later, it
is not finished until `.pages.yml` exposes it.** A JSON field with no form is
invisible: the only way to edit it is to hand-edit the repo, which is exactly
what the CMS exists to avoid, and a field nobody can see is a field that stays
at its placeholder forever.

This applies to photos, logos, PDFs and other uploads; to any text that will be
revised (a status line, a caption, a footer note); and to any toggle that
decides whether a block appears at all.

The loop for a new editable field:

1. Add the key to the right file in `src/data/` — or a new file if it belongs to
   its own sidebar entry rather than an existing one.
2. Read it in `src/lib/` and render it, with an explicit empty state. A missing
   photo should say "add a photo here", not collapse silently — an invisible
   empty slot is one nobody remembers to fill.
3. Add the field to `.pages.yml` under the matching entry, with a `description`
   that says what good input looks like. The descriptions are the only
   documentation visible while editing.
4. Rebuild and confirm the entry still loads in the CMS. A malformed field can
   break the whole form, not just itself.

Field types worth knowing: `image` gives the media picker, `file` accepts a PDF
(and needs the `categories` line above), `boolean` gives a toggle, `date` a date
picker, `object` + `list: true` a repeatable group, and `select` needs its
choices under `options.values`.

## Site shape

The site is one scrolling page. `src/pages/index.astro` stacks the sections —
hero, About, Experience, Projects, Awards, Skills, Education, Courses, Data —
and the header nav is anchors into them, with the current section highlighted as
you scroll. Contact details live in the hero and the footer rather than in a
section of their own.

The hero carries the contact row and, under it, the **Now** line: a dated
sentence saying what is currently on the bench. It is static on purpose. A live
"is he online" indicator would need a backend this site does not have, and its
common state would be "offline", which reads worse than nothing. A dated line is
honest either way — visibly fresh, or visibly stale.

Every section can be collapsed by clicking its heading. The markup ships
expanded and JavaScript upgrades the `<h2>` into a button, so the content is
there with scripting off. State is per-tab (`sessionStorage`), and a link to
`#skills` opens that section if it was closed.

Vertical rhythm is a 24px grid (`--unit`), drawn as a faint graticule behind the
page. Section heights are multiples of it, which is why fixed sizes in the CSS
tend to be odd-looking numbers like 216px — that is nine rows, not an arbitrary
choice. If you change spacing, check the section height is still divisible
by 24.

Projects still get their own pages (`/projects/<slug>/`,
`/notes/<slug>/`), because a full write-up with a spec table, a sidebar and
several interactive figures is too much to inline. The cards on the home page
link out to them, and those pages link back to `/#projects`.

Nav links are written `/#about` rather than `#about` so they also work from a
detail page.

## Deploying

Pushing to `main` triggers `.github/workflows/deploy.yml`, which builds and
publishes to GitHub Pages.

**One-time setup:** in the repository settings, under Pages, set *Source* to
**GitHub Actions**. This repo previously used the Jekyll "deploy from branch"
mode; the workflow will not publish until that is changed.

For a custom domain, add `public/CNAME` containing the domain and update `site`
in `astro.config.mjs`.

## Getting real simulation data onto the site

The charts read JSON from `public/data/`. `scripts/raw-to-json.mjs` converts
ngspice rawfiles into that format and derives DC gain, the unity-gain crossover
and phase margin from the curve itself — so the summary table under each plot
can never drift away from the trace above it.

```bash
# 1. write ASCII rawfiles (add `.option filetype=ascii` to the deck)
for c in TT FF SS FS SF; do
  ngspice -b -D corner=$c -r sim/ac_$c.raw sim/opamp_ac.spice
done

# 2. convert
node scripts/raw-to-json.mjs \
  --out public/data/opamp-ac.json \
  --node "v(out)" \
  --source simulated \
  --conditions "VDD = 1.8 V, T = 27 °C, CL = 2 pF" \
  TT=sim/ac_TT.raw FF=sim/ac_FF.raw SS=sim/ac_SS.raw \
  FS=sim/ac_FS.raw SF=sim/ac_SF.raw

# 3. flip `dataStatus: model` -> `simulated` in the project's frontmatter
```

Run `node scripts/raw-to-json.mjs --help` for the full options.

## Writing a project

Copy `src/content/projects/_TEMPLATE.mdx`. The filename becomes the URL. The
frontmatter drives the spec table, the sidebar, the index card and the filter
tags; the body is MDX, so figures are imported and placed inside the narrative:

```mdx
import BodeFigure from '../../components/BodeFigure.astro';

<BodeFigure figNo="Fig. 3" caption="What the reader should notice." />
```

Available figure components:

| Component | What it renders |
|---|---|
| `AnnotatedSchematic` | Clickable block diagram; each block explains its sizing rationale |
| `BodeFigure` | Gain/phase over log frequency, per-corner toggles, hover readout, corner summary table |
| `MonteCarloFigure` | Mismatch histogram against a spec window, with yield statistics |
| `BandgapFigure` | Linear line chart (V(ref) over temperature) with hover readout |
| `DesignExplorer` | Sliders driving the first-order op-amp model, with a live redrawn response |

Set `draft: true` to keep a page out of the build.

## Layout

```
src/
  components/     figures, header, footer, spec table, status chips
                  *Section.astro are the home page's scrolling sections
  content/
    projects/     one .mdx per project  (_TEMPLATE.mdx to copy)
    notes/        one .md per note
  layouts/        page shell, meta tags, theme handling
  data/           CMS-editable content, one file per sidebar entry:
                  now, about, experience, awards, skills, education,
                  courses, resume, footer, site
  lib/
    charts.ts       hand-rolled SVG charts (no charting dependency)
    opamp-model.ts  the first-order model behind the explorer
    site.ts         identity, merging site/resume/footer json
    about.ts        types + grouping over the section data files
    loadData.ts     chart dataset loading
    published.ts    which projects are live
  pages/          routes (index.astro is the whole one-page site)
  styles/         design tokens and component styles
.pages.yml        Pages CMS editing forms
scripts/
  gen-sample-data.mjs   generates the placeholder model datasets
  raw-to-json.mjs       ngspice rawfile -> chart JSON
public/data/      the datasets the charts fetch (and visitors can download)
```

## Notes on the design

- **Charts have no dependency.** They need log axes, engineering-notation ticks,
  phase-margin annotation and theme-aware colours; that was less work to write
  than to configure. The series palette is validated for colour-vision
  deficiency in both light and dark mode, and every chart ships a table
  alternative and a hover readout.
- **Provenance is structural, not editorial.** `dataStatus` in frontmatter drives
  a visible badge. It is deliberately hard to present a model as a measurement.
- **Conditions travel with the data.** They live in each dataset's `meta` block
  and render above the plot, so a bandwidth is never quoted without its load.
